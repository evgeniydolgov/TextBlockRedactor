# Инструкции для агентов

Проект: локальный текстовый редактор на React + TypeScript + Vite + Tiptap OSS.

OpenSpec подключён к Codex через `.agents/skills/`.
Вызов `$openspec-propose <описание>` запускает подготовку предложения.
Используйте соответствующий установленный навык; реализация вызывается через
`$openspec-apply-change`, архивация — через `$openspec-archive-change`.
В командах этих навыков заменяйте `openspec <аргументы>` на
`npm.cmd run spec -- <аргументы>`: CLI установлен локально, обёртка отключает телеметрию.

Перед работой используйте относящиеся к задаче разделы документов
(уже изученное без необходимости не перечитывайте):
1. [Процесс](docs/agents/README.md).
2. [Соглашения](docs/agents/conventions.md).
3. [Критерии готовности](docs/agents/acceptance.md).
4. [Текущую спецификацию](openspec/specs/text-editor/spec.md) и относящиеся к задаче изменения в openspec/changes/.

Сохраняйте минимальный объём продукта: текст, абзацы, H1–H3, undo/redo.
Без отдельной задачи не добавляйте backend, сохранение, облако, коллаборацию,
платные расширения, списки или перетаскивание.

Для изменения поведения сначала опишите требования и сценарии в OpenSpec.
Для исправлений в рамках существующей спецификации и небольших правок документации
достаточно краткого плана и релевантных проверок.
Действуйте в рамках запроса пользователя; не запрашивайте повторно уже данное разрешение.

Перед правками проверьте git status. Не перезаписывайте чужие изменения.
Перед завершением прочитайте diff только затронутых файлов и выполните минимальные локальные проверки.
Не объявляйте браузерную проверку выполненной по одному HTTP 200.

## Scope, контекст и проверки

Работайте строго в рамках текущего OpenSpec change и его acceptance criteria.
Не добавляйте исследования edge cases, архитектурные улучшения, рефакторинги
и потенциальные исправления, не требуемые спецификацией для текущей задачи.
Постороннюю проблему кратко зафиксируйте и продолжайте задачу; не исследуйте
и не исправляйте её без явного разрешения. Это относится и к посторонним warnings.

Экономьте контекст, токены и вычисления: читайте только необходимые фрагменты,
используйте уже полученные выводы, не исследуйте весь репозиторий ради локальной задачи.
При существенном росте контекста или необходимости изучить много дополнительных
файлов остановитесь, сообщите причину и дождитесь ответа пользователя до продолжения.

После изменения логики добавьте/обновите соответствующие unit-тесты и запустите
только тесты непосредственно затронутых модулей/функций. Используйте минимальный
type-check, если его можно корректно ограничить затронутым кодом. Если нельзя,
укажите ограничение в отчёте; не запускайте полный tsc/build как замену.
Для Markdown достаточно чтения изменённых разделов и проверки локальных ссылок.
Не выполняйте дополнительные проверки «на всякий случай». После достаточной
локальной проверки остановитесь; повторный запуск нужен только после влияющих
на результат правок или исправления ошибки.

Full Quality Gate запрещён до явной команды пользователя, например
`Run full quality gate`. Только она разрешает полный suite, глобальный coverage,
полные lint/type-check, production build, OpenSpec validation, diff-check
и другие глобальные проверки. Обычные propose/apply/archive не являются разрешением.
Не запрашивайте полный gate автоматически. Чтение diff и статуса OpenSpec разрешено.
Даже полный gate не разрешает исправления вне scope или браузерные проверки
без отдельного прямого запроса. Старые планы с обязательным полным gate не отменяют
эту политику; невыполненные проверки не объявляйте пройденными.

## CSS и проверки

В CSS пишите каждую декларацию на отдельной строке внутри селектора, с отступом
2 пробела на уровень. Закрывающая скобка — на отдельной строке. Между правилами
оставляйте пустую строку, между каждой парой деклараций — не оставляйте.
Это относится и к псевдоклассам, и к правилам внутри media queries.

Не запускайте браузерные проверки без прямого запроса пользователя на такую проверку.
Запрет включает headless, открытие вкладок, скриншоты, браузерные стенды и косвенное
открытие через dev-команду с auto-open. Обычная задача реализации или рефакторинга
не разрешает браузерную проверку. Не запрашивайте её автоматически при каждой задаче.
Выполняйте только локальные CLI-проверки по политике выше; UI-сценарии передавайте пользователю для ручной
проверки. В отчёте отделяйте результаты CLI от UI-проверок, которые не выполнялись
по правилу проекта. Их отсутствие само по себе не блокирует завершение задачи.

## Коммиты выполняет пользователь

Агент не создаёт коммиты, не выполняет amend и не переписывает историю.
Не выполняйте git add и другие операции изменения индекса; уже подготовленные
пользователем файлы оставляйте в индексе без изменений.
После работы сообщите результат и проверки и предложите название коммита.
Если изменений файлов нет, название коммита не предлагайте.
Коммит пользователь создаёт вручную. Не запрашивайте разрешение сделать это за него.
Правило действует и при завершении OpenSpec apply/archive.
Не предлагайте включать node_modules, dist, секреты и журналы в коммит.
