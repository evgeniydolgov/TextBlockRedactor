# Работа с агентами

## Карта документов

- [AGENTS.md](../../AGENTS.md) — короткая точка входа.
- [conventions.md](conventions.md) — правила реализации и коммитов.
- [task-template.md](task-template.md) — исходная постановка задачи.
- [acceptance.md](acceptance.md) — общий критерий готовности.
- [openspec/specs/](../../openspec/specs/) — актуальное поведение продукта.
- [openspec/changes/](../../openspec/changes/) — предлагаемые изменения и архив.
- [openspec/config.yaml](../../openspec/config.yaml) — контекст для CLI.

Требования к продукту хранятся в спецификациях. Правила работы — в этих документах.
Не дублируйте требования в нескольких местах.

## Установка и команды

Основной вход — команда в чате Codex:

```text
$openspec-propose Описание желаемого изменения
```

Она создаёт предложение, спецификации и задачи. Для реализации затем вызовите
`$openspec-apply-change <имя-изменения>`, для архивации —
`$openspec-archive-change <имя-изменения>`.
Если новые навыки ещё не появились в списке, откройте новую сессию проекта.

После клонирования выполните `npm.cmd ci`. OpenSpec закреплён в devDependencies,
глобальная установка не требуется. На macOS/Linux используйте npm вместо npm.cmd.

```powershell
npm.cmd run spec -- --version
npm.cmd run spec -- list
```

`npm.cmd run spec:validate` — глобальная проверка, агент запускает её только
по явной команде полного quality gate; наличие команды в документации не разрешает запуск.

Обёртка scripts/openspec.mjs отключает телеметрию для этих команд.
Интеграция Codex установлена через `init --tools codex --profile core`.
Официальные навыки находятся в `.agents/skills/`. Codex использует вызов
`$openspec-propose`; отдельную slash-команду `/opsx:propose` эта интеграция не создаёт.
Команды CLI из навыков агент запускает через `npm.cmd run spec -- ...`.
Файлы спецификаций и изменения хранятся локально в Git.
Не запускайте повторный init для обычной задачи.

## Рабочий цикл

1. Прочитайте задачу, git status и текущую спецификацию. Обозначьте цель,
   границы и критерии по [шаблону](task-template.md).
2. Для нового поведения создайте изменение с коротким именем kebab-case:

```powershell
npm.cmd run spec -- new change add-local-save
npm.cmd run spec -- instructions proposal --change add-local-save
```

Имя add-local-save — пример, а не поручение реализовать сохранение.

3. Следуйте инструкциям схемы spec-driven. Создайте proposal.md (зачем и что),
   specs/<capability>/spec.md (изменения требований),
   design.md (решения и компромиссы), tasks.md (проверяемые шаги).
   Получайте шаблоны и зависимости через CLI:

```powershell
npm.cmd run spec -- status --change add-local-save
npm.cmd run spec -- instructions specs --change add-local-save
npm.cmd run spec -- instructions design --change add-local-save
npm.cmd run spec -- instructions tasks --change add-local-save
```

4. В delta-спецификации используйте разделы ADDED/MODIFIED/REMOVED Requirements.
   В MODIFIED включайте полное требование и его сценарии. Сохраняйте служебные
   заголовки Requirement/Scenario и ключевые слова SHALL, WHEN, THEN на английском.
   Пояснения пишите по-русски.
5. Прочитайте изменённые артефакты и проверьте их согласованность и локальные ссылки.
   Реализуйте только поставленную задачу; существенное расширение границ обсудите с пользователем.
6. Выполните минимальные проверки затронутой области, отметьте выполненные пункты tasks.md.
   В отчёте перечислите результат, проверки и ограничения. Если файлы изменены,
   предложите название коммита в формате `type(scope): описание`.
7. После завершения изменения архивируйте его по запросу пользователя:

```powershell
npm.cmd run spec -- archive add-local-save --yes
```

Архивация обновляет основные спецификации из delta-файлов и переносит изменение
в changes/archive/. Проверьте diff. Не архивируйте незавершённую работу и не
отключайте защитные проверки CLI. Если операция требует запрещённой проверки,
сообщите об этом пользователю до запуска, не обходите запрет.
Для чисто инфраструктурного изменения без delta допустим
флаг --skip-specs с пояснением причины.

Исправления без изменения требований и мелкие правки Markdown могут идти напрямую.
Не создавайте фиктивные продуктовые изменения ради документации.

## Локальные проверки и Full Quality Gate

По умолчанию агент проверяет только непосредственно изменённую область: конкретные
unit-тесты и минимальный доступный type-check. Например:
`npm.cmd test -- src/editor/limits/fitInsertion.test.ts`.
Для Markdown достаточно чтения изменённых разделов, их diff и локальных ссылок.
Если корректный локальный type-check невозможен, укажите ограничение без полного build.

Полный suite, глобальные coverage/lint/type-check, production build, OpenSpec
validation, diff-check и другие глобальные проверки запрещены до явной команды
пользователя, например `Run full quality gate`. Propose/apply/archive не являются
таким разрешением. Не добавляйте gate в каждую задачу и не запрашивайте автоматически.
Состав разрешённого gate — в [acceptance.md](acceptance.md).

Scope ограничен текущим change и его acceptance criteria. Посторонние проблемы
кратко фиксируйте без исследования и исправления. Читайте только нужные фрагменты,
не перечитывайте изученное без причины. При существенном росте контекста или
необходимости изучить много дополнительных файлов остановитесь до ответа пользователя.
После достаточной локальной проверки завершайте работу; повторный запуск оправдан
только влияющими на результат правками. Не выполняйте проверки «на всякий случай».

Браузерные/E2E/визуальные проверки, включая headless, вкладки, скриншоты и стенды,
допустимы только по прямому запросу пользователя на такую проверку.
Поручение реализации, рефакторинга или полного CLI gate не является таким запросом.
Не открывайте браузер косвенно через auto-open и не запрашивайте разрешение
на UI-проверку автоматически при каждой задаче.

Непроверенные UI-сценарии передавайте пользователю для ручной проверки.
В отчёте отдельно перечисляйте выполненные CLI-проверки и указывайте, что браузерные
проверки не выполнялись по правилу проекта. Их отсутствие само по себе не блокирует
завершение задачи, но не подтверждает правильность интерфейса.

## Передача результата и ручной коммит

Агент завершает задачу отчётом и предложением названия коммита при наличии изменений.
Подготовку индекса и создание коммита пользователь выполняет вручную.
Агент не выполняет git add, git commit, amend или другие операции изменения
индекса и истории; уже подготовленные пользователем файлы сохраняются в индексе.
Завершение OpenSpec apply/archive не меняет это правило и не является разрешением
на автоматический коммит. Не запрашивайте разрешение сделать коммит за пользователя.
Если файлы не менялись, достаточно отчёта без предложенного названия.
