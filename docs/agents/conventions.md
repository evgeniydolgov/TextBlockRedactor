# Соглашения

## Реализация

- TypeScript, функциональные React-компоненты, обычный CSS.
- Сохраняйте стиль существующего кода: 2 пробела, одинарные кавычки, без точек с запятой.
- Компоненты — PascalCase, функции и переменные — camelCase.
- Один экземпляр Tiptap на документ. Не дублируйте его содержимое в React state.
- Расширения подключайте в src/editor/extensions.ts; UI редактора — в src/editor/.
- initialContent — только начальный NoteDocument (массив блоков); onChange передаёт
  последний массив в том же формате после паузы saveDelayMs (по умолчанию 1000 мс).
  Новый ввод перезапускает ожидание; при уходе/cleanup ожидающий снимок передаётся сразу.
  Tiptap JSON остается внутренним представлением. localStorage подключён на уровне
  страницы; ключ text-block-redactor:note:v1, значение — JSON-массив NoteDocument.
- При split старый ID всегда у первого фрагмента, даже пустого; второй получает новый.
- Все новые ID сущностей данных генерируйте через createId из src/shared/ids.ts
  (UUID v7), включая будущие сущности. Входные существующие ID сохраняйте без
  проверки версии UUID и без перегенерации; проверки непустой строки и дубликатов остаются.
- Не добавляйте зависимости без конкретной необходимости. Для новых пакетов проверьте
  лицензию и совместимость; сохраняйте package-lock.json вместе с package.json.
- Пользовательские подписи — по-русски; сохраняйте доступные подписи и управление с клавиатуры.

## CSS

Каждая декларация — на отдельной строке, отступ — 2 пробела на уровень.
Закрывающая скобка — на отдельной строке. Пустая строка разделяет правила,
но не каждую пару деклараций. Формат действует для классов, других селекторов,
псевдоклассов и правил внутри media queries:

```css
.editor-toolbar {
  display: flex;
  gap: 4px;
  padding: 8px 0;
}
```

## Документы

- UTF-8; в Windows PowerShell читайте русский текст через Get-Content -Encoding UTF8.
- Короткие инструкции, относительные ссылки, проверенные команды.
- Новые требования описывайте наблюдаемым поведением и сценариями WHEN/THEN.
- Не выдавайте планы за реализованные возможности.
- Не переносите технические инструкции в интерфейс продукта.

## Проверки и Git

- В PowerShell используйте npm.cmd: npm.ps1 может блокироваться политикой выполнения.
- Не запускайте второй Vite для той же папки. Адрес проекта: http://127.0.0.1:3000.
- Не завершайте неизвестный процесс ради освобождения порта.
- Тестируйте изменённое поведение. Не добавляйте тестовый фреймворк ради правки Markdown.
- По умолчанию используйте подходящие CLI-проверки: build, lint, OpenSpec validate
  и проверки кода. Браузерные проверки выполняйте только по прямому запросу
  пользователя на них; обычный запрос реализации или рефакторинга таким запросом не является.
- Не запускайте без такого запроса headless, вкладки, скриншоты, браузерные стенды
  и dev-команды с auto-open ради проверки. Не запрашивайте разрешение автоматически
  при каждой задаче. Настройки запуска приложения самим пользователем не меняйте.
- Непроверенные UI-сценарии передавайте пользователю и явно отмечайте в отчёте:
  «не выполнялось по правилу проекта». CLI-проверки не доказывают корректность UI;
  отсутствие браузерной проверки само по себе не блокирует завершение задачи.
- Коммиты пользователь создаёт вручную. Агент не выполняет git commit, amend
  и операции переписывания истории; не запрашивает разрешение сделать коммит за пользователя.
- Агент не выполняет git add и другие операции изменения индекса.
  Уже подготовленные пользователем файлы остаются в индексе без изменений со стороны агента.
- При фактических изменениях файлов предложите название коммита в формате
  `type(scope): конкретное действие`, соответствующее одному логическому результату.
  Примеры названий: `docs(agents): document task workflow`;
  `chore(openspec): initialize project specs`. Это только предложения текста.
- Если изменений файлов нет, не предлагайте название коммита.
- Завершение обычной задачи или OpenSpec apply/archive не разрешает создание коммита.
- Не отправляйте изменения в remote без запроса пользователя.
