# Проверка запросов блоков

После паузы saveDelayMs (по умолчанию 1000 мс) страница сравнивает текущие блоки
с последним обработанным снимком и выводит массив объектов под `[note:requests]`.
При уходе ожидающий снимок обрабатывается сразу. Сам preview не выполняет HTTP.
Лог `[note:blocks]` и сохранение полной заметки продолжают работать.

## Очередь PUT существующих блоков

Отдельная очередь получает итоговый снимок после успешного локального сохранения.
Её необязательный адаптер `putBlock(block)` принимает полный блок с прежним ID;
реальный адаптер может обращаться к серверу. На странице по умолчанию подключён
демонстрационный адаптер в памяти без HTTP. Можно передать `putBlock` и доверенный
`confirmedBlocks` через `DocumentPage`; при отсутствии доверенной базы отправка
не начинается. Передача `putBlock={null}` отключает очередь.

Одновременно идут не более четырёх PUT разных ID. Для одного ID следующий PUT
начинается только после успешного ответа на предыдущий и берёт последнюю версию
блока. Пока ответ не пришёл, пользователь продолжает редактировать. Ошибка или
таймаут останавливают PUT этого ID без автоматического повтора, но не мешают
другим ID. В интерфейсе отдельно видны локальное сохранение, синхронизация и ошибка.

Подтверждённые блоки и отметки о начатых PUT хранятся отдельно под ключом
`text-block-redactor:put-sync:v1`. Черновик записывается до отправки; отметка
о начале PUT — до вызова адаптера. После перезагрузки ID с неизвестным исходом
не отправляется автоматически: сначала будущая интеграция должна выяснить его
состояние на сервере. Новые и удалённые блоки остаются только в preview, поэтому
страница не объявляет всю заметку синхронизированной с сервером при таких изменениях.
При отказе localStorage восстановление правок после закрытия не гарантировано;
неподтверждённые изменения не попадут на сервер, если страницу больше не открыть.

## Контракт

| Операция | Метод и путь | body |
| --- | --- | --- |
| Один новый блок | POST /blocks | `{ block, position }` |
| Изменённый существующий блок | PUT /blocks/:blockId | Полный текущий блок |
| Один удалённый блок | DELETE /blocks/:blockId | Поле отсутствует |
| Несколько новых блоков подряд | POST /blocks/list | `{ operation: 'CREATE', blocks, position, noteId? }` |
| Несколько удалённых блоков | POST /blocks/list | `{ operation: 'DELETE', ids, noteId? }` |

noteId можно передать через `<DocumentPage noteId="..." />`. Он включается только
в групповые запросы; без пропса поле отсутствует. Создание заметки не реализовано.
ID блоков не меняются, в сегменте пути используется encodeURIComponent.
В тела не добавляются поля ответа NoteBlockDTO и числовой position.

## Порядок и позиции

Сначала удаления, затем обновления в текущем порядке, затем создания слева направо.
`before` — предыдущий блок, `after` — следующий, отсутствующий сосед равен null.
Для `[A, X, Y, B]` новая группа `[X, Y]` получает
`position: { before: A.id, after: B.id }`. Одна группа сохраняет порядок массива.
Новые блоки, разделённые сохранившимися, образуют отдельные запросы.
При замене `[A, B, C, D]` на `[A, X, Y, D]` сначала удаляются B/C, затем X/Y
создаются между A/D. Сдвиг индексов существующих блоков не создаёт PUT.

## База сравнения

Начальные блоки редактора и preview одинаковы, включая ID пустого начального блока.
Они уже обработаны [лимитами содержимого](content-limits.md): длинные блоки разбиты,
лишний хвост отброшен. Эта нормализация при mount не сохраняет заметку и не выдаёт
CREATE/DELETE для отличий от старой записи localStorage.
Mount не создаёт запросов. Первый ввод в начальный пустой блок даёт PUT.
Ввод и полная отмена до паузы дают пустой список операций.
Если удаление уже было обработано, undo создаёт восстановленный блок с прежним ID.

База preview обновляется после каждого построения запросов независимо от успеха localStorage.
Повторный снимок не повторяет операции. После reload база берётся из загруженной
заметки, а не из диагностической записи. Это локальная проверка формата, не состояние
сервера и не очередь доставки. Очередь PUT ведёт собственную подтверждённую базу.
Перестановки существующих блоков не поддерживаются:
MOVE, искусственные DELETE/CREATE и групповое UPDATE не формируются.

## Последний цикл в localStorage

`text-block-redactor:note:v1` хранит полную заметку.
`text-block-redactor:request-log:v1` хранит один JSON-объект:

```ts
{
  requests: [ /* { method, path, body? } */ ],
  storage: {
    key: 'text-block-redactor:note:v1',
    data: [ /* полный документ, переданный на сохранение */ ],
    success: true,
    error: null
  }
}
```

Каждый цикл полностью заменяет запись, даже если requests пустой. Истории,
временных меток и ID цикла нет. success/error описывают попытку основной записи.
Если она не удалась, data всё равно содержит переданный документ, success — false,
error — сообщение ошибки. Ошибка самой диагностической записи выводится через
console.warn и не меняет результат сохранения заметки; старая запись может остаться.
Mount, выделение и flush без ожидающих изменений не перезаписывают диагностику.
Отклонённый ввод также не создаёт цикл и не сдвигает ожидающее сохранение.
Один принятый ввод с авторазбиением даёт один итоговый снимок без промежуточного
превышения; продолжения получают CREATE. При уменьшении лимитов нормализованный
снимок заменяет ожидающий, поэтому при уходе сохраняется уже обрезанная версия.

## Ручная проверка

Эти сценарии агент в браузере не выполняет без прямого запроса пользователя.

- В Console отфильтровать `[note:requests]`, изменить текст и дождаться паузы: один PUT.
- Нажать Enter: CREATE нового блока, при изменении первого — также PUT.
- Вставить несколько блоков: соседние новые блоки объединены в групповой CREATE.
- Удалить несколько блоков: групповой DELETE, ids в порядке старого документа.
- Изменить текст и отменить до паузы: нет новых запросов, последний цикл имеет requests: [].
- В Application → Local Storage проверить ключ request-log: метод, путь, body,
  полный storage.data и результат записи; следующий цикл заменяет предыдущий.
- После ввода сразу скрыть вкладку: ожидающий цикл записан, повторного запроса нет.
- Обновить страницу: заметка восстановлена, mount не создаёт запросов и не меняет журнал.

Unit-тесты используют снимки блоков, fake timers и storage-заглушки;
внутренности Tiptap, UI и backend не тестируются.
