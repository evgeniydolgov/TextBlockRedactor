# Design

## Context

См. [proposal.md](proposal.md) и delta specs. Сейчас `createDebouncedChange` передаёт последний документ в `createNoteSaveHandler`: тот сохраняет полный массив в `text-block-redactor:note:v1` и отдельно формирует диагностический preview. `createRequestPreview` сдвигает свою базу при построении описаний запросов, независимо от результата локального сохранения. Эту базу нельзя использовать как подтверждение PUT. Существующий `onChange` приходит после `saveDelayMs`, а при обычном уходе ожидающий снимок синхронно передаётся локальному сохранению.

## Goals / Non-Goals

**Goals:**

- Сделать PUT существующих серверных блоков упорядоченными по ID при параллельной работе разных ID.
- Восстановить локальные неподтверждённые правки после обычного закрытия и не повторять автоматически PUT с неизвестным исходом.
- Не менять семантику preview и формат `NoteDocument`.

**Non-Goals:**

- Гарантировать доставку HTTP после закрытия вкладки или при отказе localStorage.
- Синхронизировать CREATE/DELETE, обеспечивать несколько одновременных клиентов либо разрешать конфликты без серверных версий.

## Decisions

### Отдельная серверная база и явная инициализация

Очередь хранит подтверждённые снимки по ID отдельно от `createRequestPreview`, текущего документа и диагностического журнала. При подключении адаптера вызывающая сторона передаёт доверенный начальный снимок существующих серверных блоков либо очередь восстанавливает ранее сохранённый подтверждённый снимок для той же заметки. Если нет ни того ни другого, очередь остаётся неинициализированной и PUT не запускает: загруженная из localStorage заметка сама по себе не доказывает наличие блоков на сервере. Демонстрационный адаптер может явно считать переданный ему начальный документ своим имитированным серверным состоянием; это допущение демонстрации, не гарантия для реального сервиса. Альтернатива — автоматически объявить localStorage серверной базой — скрыла бы несохранённые ранее изменения.

### Восстановление из черновика и подтверждений

Формат `NoteDocument` и его ключ не меняются. Для очереди вводится отдельная версия записи с идентификатором заметки, подтверждёнными блоками и отметками о начатых или остановленных PUT по ID. Текущие ещё не отправленные изменения вычисляются сравнением последнего локального документа с этой базой. Сначала синхронно записывается локальный документ существующим механизмом, затем до отправки PUT сохраняется отметка о нерешённом запросе. Если запись отметки не удалась, запрос не начинается. После успешного PUT **ровно отправленный снимок** и снятие отметки записываются вместе в одной записи состояния очереди. При ошибке или таймауте отметка остаётся блокирующей; после перезагрузки нельзя автоматически повторять этот PUT, даже если успех ответа не успел записаться. Диагностический `request-log:v1` не служит журналом очереди.

Локальный документ и состояние очереди записываются в разные ключи, поэтому атомарности между ними нет. При восстановлении состояние должно быть привязано к идентификатору заметки, содержать только подтверждённые снимки и отметки неизвестного исхода; более новый локальный документ никогда не заменяется им. Если запись локального документа или состояния очереди повреждена/недоступна, показывается ошибка и нельзя заявлять гарантию восстановления. Альтернатива — единый новый ключ для заметки и очереди — меняла бы существующий контракт локального сохранения.

### Планировщик по ID

`putBlock(block)` получает копию полного блока и возвращает успешно завершённый Promise только после подтверждения операции адаптером. Максимум четыре PUT разных ID одновременно; для одного ID — не больше одного. После задержки `saveDelayMs` планировщик сравнивает актуальные блоки с подтверждёнными. Пока версия A блока 2 выполняется, версии B и C не создают дополнительных запросов: только после успешного ответа на A планировщик снова сравнивает A с последним локальным C и отправляет C. Ответы никогда не записываются в редактор. Альтернатива — одна очередь на всю заметку — сохраняла бы порядок, но задерживала независимые блоки из-за медленного ответа одного ID.

Пока Promise адаптера не завершён, PUT того же ID не отправляется, сколько бы ни длилось ожидание. Адаптер отвечает за ожидание сервера и, если оно превышено, завершает Promise ошибкой. Любая ошибка или таймаут оставляет ID неподтверждённым и блокирует новые PUT этого ID без автоматического повтора; страница показывает ошибку. Остальные ID продолжают работу. После перезагрузки сохранённая отметка о начатом запросе также блокирует автоматическую отправку: исход мог остаться неизвестным. Разблокировка после выяснения исхода сервером относится к будущей интеграции, а не к этому демонстрационному этапу.

### Только существующие блоки и честный статус

PUT допускается лишь для ID в доверенной серверной базе. Новый ID не отправляется как PUT; если исходный блок исчез, после завершения уже выполняющегося PUT не ставится следующий PUT. CREATE/DELETE остаются в существующем preview, а состояние страницы не может стать «полностью синхронизировано», пока есть такие структурные различия. Локальная запись, активная/ожидающая отправка, ошибка и отсутствие доверенной базы показываются раздельно. Адаптер без HTTP используется в локальном примере и адресных тестах: управляемая задержка, успешный ответ и отказ; реальный сервис подключается позже без изменения очереди.

### Последовательности

- **Четыре блока:** после паузы локальный документ с изменениями 2/4/6/8 записан целиком; планировщик одновременно запускает до четырёх PUT по этим ID. Ответы могут прийти в любом порядке, потому что каждый ID подтверждается отдельно. Блоки 1/3/5/7/9/10 не отправляются.
- **Повторная правка:** PUT блока 2 отправил A; пока он выполняется, локально появились B и C. Успешный ответ подтверждает A, затем запускается один PUT C. Ни A, ни ответ не заменяют C в редакторе.
- **Ошибка:** PUT блока 2 не подтвердился, остальные блоки могут подтвердиться. Блок 2 остаётся неподтверждённым, его новые PUT останавливаются и страница показывает ошибку; подтверждённая база блока 2 не продвигается.
- **Перезагрузка:** ожидающий снимок при обычном уходе записывается в localStorage; HTTP не ожидается. После открытия берутся последний локальный документ, ранее подтверждённая база и отметки нерешённых запросов. Ещё не отправленные изменения существующих ID могут отправляться; ID с начатым, но не подтверждённым PUT остаются заблокированными до будущей сверки с сервером.

## Risks / Trade-offs

- [Первое подключение без доверенной серверной базы] → не отправлять PUT и показывать неинициализированное состояние; реальная интеграция должна передать подтверждённый снимок.
- [Разрыв между записью локального документа и состоянием очереди] → порядок «черновик, отметка о начатом PUT, отправка, запись подтверждения»; неопределённое состояние не трактовать как успех и не повторять автоматически.
- [Сервер не ответил до закрытия страницы] → локальные правки сохраняются, но их серверное применение остаётся неизвестным; без будущей сверки с сервером автоматическая отправка этого ID не возобновляется.
- [localStorage переполнен или недоступен] → сохранить ввод в памяти текущей вкладки, показать отсутствие гарантии восстановления; абсолютную сохранность обещать нельзя.
- [CREATE/DELETE не отправляются] → показывать частичную синхронизацию, не утверждать, что серверная заметка целиком совпадает с локальной.
- [Другие вкладки/устройства или сервер меняется вне этой очереди] → гарантии порядка не действуют; версия/условная запись сервера потребуется отдельным change.

## Migration Plan

Существующие ключ заметки и диагностического журнала остаются без изменений. Новый ключ подтверждённой базы создаётся только при включённой очереди и наличии доверенного начального состояния. Старые локальные заметки без такой базы продолжают редактироваться локально; автоматическая отправка их блоков запрещена до инициализации. При отключении адаптера локальный редактор и preview продолжают работать, а сохранённое состояние очереди не выдаётся за подтверждение сервера.
