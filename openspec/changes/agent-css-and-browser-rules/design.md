# Design

## Context

См. proposal.md. Требование браузерной проверки сейчас есть в acceptance.md и
в пунктах 3.3–3.4 активного modularize-text-editor. Простой запрет только в AGENTS.md
оставил бы противоречащие ему обязательные шаги. CSS уже разделён на модули,
но содержит избыточные пустые строки между декларациями.

## Goals / Non-Goals

**Goals:** согласованные правила форматирования и проверки, экономия токенов,
честный отчёт о непроверенном поведении.

**Non-Goals:** изменение продукта, установка форматтера, массовая правка CSS,
отмена CLI-проверок или запрет ручной проверки пользователем.

## Decisions

Формат CSS закрепить примером в conventions.md и кратким правилом в AGENTS.md:

```css
.editor-toolbar {
  display: flex;
  gap: 4px;
  padding: 8px 0;
}
```

Правило действует также внутри media queries и псевдоклассов. Отступ — 2 пробела
на уровень. Автоматический линтер не нужен для этой документационной задачи.

Браузерные проверки требуют прямого запроса пользователя, включая headless и
браузерный стенд. Не открывать браузер косвенно через dev-команду с auto-open
ради проверки. Build, lint, OpenSpec validate и проверки кода разрешены как обычно.
Не менять настройки пользовательского запуска Vite в этой задаче.

В acceptance.md UI-сценарии обозначить как ручные или выполняемые агентом по
прямому запросу. В отчёте явно писать «не выполнялось по правилу проекта».
Отсутствие UI-проверки само по себе не блокирует завершение задачи, но не является
доказательством работоспособности интерфейса. HTTP 200 также им не является.

При применении обновить оставшиеся пункты modularize-text-editor: 3.3 — передать
список ручной регрессии и зафиксировать отсутствие браузерной проверки; 3.4 —
проверить JSON-контракт по коду, описать непроверенные runtime-сценарии пользователю,
не создавать браузерный стенд. Не отмечать исходные тесты как пройденные.
Альтернатива с сохранением обязательных UI-тестов противоречит новому запросу.

## Risks / Trade-offs

- Визуальные регрессии могут остаться незамеченными → сообщать границы CLI-проверок
  и коротко перечислять ручные сценарии без самостоятельного запуска браузера.
- Старые планы могут требовать UI-тестов → согласовать активный план при применении,
  сохранив выполненную работу и историю фактических проверок.
