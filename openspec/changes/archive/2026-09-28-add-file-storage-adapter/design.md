# Design

## Context

См. [proposal.md](proposal.md). Сейчас `FileNode.ts` рисует неактивную кнопку; `fileProps` типизированы как пустые литералы, `blocksToTiptap.ts` передаёт для file только ID блока, а `tiptapToBlocks.ts` создаёт пустую заготовку. Для image уже есть независимый адаптер, контроллер его экземпляра, NodeView и отдельная асинхронная логика. Основная спецификация `text-editor` пока описывает исходный текстовый редактор; существующие изменения OpenSpec описывают заготовки и image. Этот delta добавляет новое поведение file и заменяет для него прежнее ограничение на пустые props и неактивную кнопку, не меняя image.

## Goals / Non-Goals

**Goals:** разделить сериализуемую ссылку на файл и временное состояние интерфейса; сделать контракт файлового хранилища заменяемым; безопасно обновлять ровно исходный блок после асинхронной загрузки; получать файл только по действию пользователя.

**Non-Goals:** общее хранилище для image и file, фоновое получение файлов, восстановление бинарных данных после перезагрузки демонстрационной страницы, удаление файла из хранилища при undo или удалении блока.

## Decisions

1. **Отдельный контракт файлов.** Добавить `FileStorageAdapter` с `upload(file: File): Promise<{ id: string; name: string }>` и `resolve(fileId: string): Promise<{ type: 'url'; url: string } | { type: 'blob'; blob: Blob }>`; прокинуть его через необязательный `TextEditorProps.fileStorage`. Контроллер, созданный в `useTextEditor`, позволит NodeView брать актуальный экземпляр адаптера без пересоздания редактора. Это повторяет границу image без изменения его файлов. Альтернатива — общий базовый адаптер и рефакторинг image — увеличила бы объём и риск без пользы для текущей задачи. При отсутствии адаптера file-блок остаётся видимым, а операции выбора/скачивания недоступны.

2. **Стабильная модель заметки.** Расширить только тип file props: `url`, `name`, `caption` — строки, остальные поля сохраняют текущие значения по умолчанию. File-узел Tiptap получит соответствующие attrs; оба преобразования и `validateNote` сохранят непустые значения. В `url` хранится только непрозрачный ID, а не адрес, Blob или путь; имя берётся из результата адаптера. Нового формата localStorage и миграции не требуется: прежние пустые блоки остаются корректными. Альтернатива — сохранять прямой URL/Blob — сделала бы заметку зависимой от транспорта и нарушила бы требование о хранении только метаданных.

3. **NodeView и локальное асинхронное состояние.** File NodeView содержит скрытый `<input type="file">` без `accept`, кнопку выбора, имя и кнопку скачивания. Выбор одного файла запускает upload; состояние `idle/loading/error` живёт вне документа. Пока loading, повторный выбор недоступен. При ошибке props не меняются и кнопка снова доступна. Отдельная операция скачивания запускает `resolve` только по нажатию; её ошибка отображается локально с возможностью повторить. Смена адаптера влияет на последующие действия, но не меняет сохранённый ID.

4. **Защита от устаревших ответов.** Контроллер загрузки инвалидирует результат при уничтожении NodeView. Перед транзакцией команда проверяет, что по `getPos()` находится именно file-узел с исходным ID и ещё пустой ссылкой; это предотвращает запись в другой блок после изменения структуры документа. Успех меняет только `url` и `name` через транзакцию Tiptap с отдельной границей истории, как image; `caption` сохраняется. Пользователь продолжает редактирование, а текущий пустой блок и последующее заполнение проходят через существующий `onChange` и debounce. Альтернатива — хранить результат до завершения всей заметки — привязала бы загрузку к сохранению и мешала бы обычному редактированию.

5. **Скачивание и владение временным URL.** Для ответа URL NodeView инициирует браузерное скачивание по предоставленному адаптером адресу. Контракт предполагает адрес, доступный браузеру для скачивания; серверные заголовки, авторизация и CORS остаются ответственностью конкретного адаптера/сервиса. Для Blob NodeView создаёт object URL, запускает скачивание с сохранённым именем и освобождает созданный URL после использования и при уничтожении. Результат позднего запроса игнорируется, если блок уничтожен или его файловый ID изменился. Разрешённый URL не записывается в заметку и не освобождается редактором.

6. **Демонстрационная реализация.** `createMemoryFileStorage` хранит `Map<string, Blob>` в памяти модуля/страницы, назначая ID через `createId`, и возвращает исходное имя. `DocumentPage` создаёт и передаёт её аналогично image. После перезагрузки metadata из localStorage остаются, но `resolve` выдаёт понятную ошибку отсутствия файла; интерфейс позволяет повторить скачивание. Это показывает контракт, не создавая фиктивной постоянности.

## Risks / Trade-offs

- [Сохранённый ID без Blob после перезагрузки демо-адаптера] → оставить блок видимым и выводить локальную ошибку скачивания; настоящий сервис позже заменит адаптер.
- [Удаление или перемещение блока во время upload] → проверять исходный ID/тип непосредственно перед транзакцией и инвалидировать уничтоженный NodeView.
- [URL внешнего сервиса может открыться в браузере вместо скачивания] → задокументировать требование к URL как к доступному для скачивания ресурсу; для надёжного имени сервис может вернуть Blob.
- [Быстрый revoke object URL может прервать скачивание] → освобождать после запуска браузерного действия, а также при уничтожении NodeView; проверять локальной unit-логикой владения URL.

## Migration Plan

Схема заметки остаётся прежней: пустые file-блоки и старые текстовые документы читаются как раньше. При откате заполненный file-блок в старом коде не сможет пройти прежнюю валидацию; откат потребует возврата новой реализации или очистки таких ссылок из сохранённой заметки. В рамках текущего изменения автоматическую миграцию не добавлять.
