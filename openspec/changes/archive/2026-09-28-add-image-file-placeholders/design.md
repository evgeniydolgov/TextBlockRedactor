# Design

## Context

Мотивация и границы — в [proposal.md](proposal.md), наблюдаемое поведение — в [delta specs](specs/text-editor/spec.md). Design нужен, поскольку изменение затрагивает модель, транзакции, лимиты и сохранение.

В текущем коде NoteBlock, validateNote и оба конвертера поддерживают только paragraph/heading. blockText и diffBlocks вызывают content.map; normalizeNote при обрезке добавляет content даже исходному блоку. UniqueID зарегистрирован только для текстовых типов. Панель строится из команд преобразования текущего текстового блока, поэтому команды добавления вложений должны быть отделены от этого списка.

Основная text-editor spec пока описывает ранний редактор без сохранения. Реализованные изменения blocknote-compatible-note-model, debounce-local-note-save и limit-note-content остаются неархивированными. Это известное расхождение: новый change дополняет фактический NoteDocument и не откатывает сохранение/лимиты к старой спецификации. Синхронизация старых changes вне этой задачи; при последующей архивации следует согласовать их порядок, чтобы раннее требование о только текстовом подмножестве не перекрыло расширение image/file.

## Goals / Non-Goals

**Goals:** нетекстовые заготовки в едином Tiptap-документе и существующем цикле сохранения, минимум нового UI, стабильные ID и история.

**Non-Goals:** общий framework вложений, upload API или скрытый file input, отдельный React state документа, изменение схемы хранения, настройка props через интерфейс. Полный список исключений — в proposal.

## Decisions

### 1. Расширить discriminated union NoteBlock

Общими остаются id и children: []; текстовый content относится только к paragraph/heading. Для image/file допускается content?: undefined. Их props задаются отдельными типами, без наследования textColor от текстовых блоков.

Defaults из [документации BlockNote](https://www.blocknotejs.org/docs/features/blocks/embeds):

| Поле | file | image |
| --- | --- | --- |
| backgroundColor | default | default |
| name / url / caption | пустые строки | пустые строки |
| textAlignment | отсутствует | left |
| showPreview | отсутствует | true |
| previewWidth | отсутствует | undefined |

В JSON content и previewWidth со значением undefined опускаются. Валидация принимает отсутствие этих полей и undefined, но не подменяет их массивом [] или null. На этом этапе валидны только пустые props с defaults: произвольные URL и непустые подписи не означают поддержку загруженных вложений. Конвертеры сохраняют семантически одинаковый формат после JSON round trip. Старые текстовые блоки не меняются.

Альтернатива content: [] для всех типов проще для существующих циклов, но расходится с моделью BlockNote. Установка самого BlockNote ради типов не нужна.

### 2. Два атомарных узла с общей простой заготовкой

Добавить image/file как selectable block atom без inline content и drag-and-drop. Зарегистрировать их в extensions.ts и uniqueIdOptions. Использовать существующие возможности Tiptap для представления узла: оболочка выделяемого блока, disabled-кнопка, без contentDOM и file input. Общую разметку двух типов можно вынести в небольшой helper; React NodeView нужен только если необходим для корректного выделения, отдельного состояния вложения нет.

Выделение должно работать по оболочке и с клавиатуры независимо от disabled-кнопки. Видимая рамка обозначает выделенный блок. Выбранный image/file не должен давать ложное активное состояние «Текст» и не преобразуется кнопками H1–H3/«Текст»; эти команды недоступны для такого выделения. Существующие текстовые режимы сохраняются.

Альтернатива вставлять декоративный React-элемент вне документа не обеспечивает штатные ID, порядок, сохранение и историю.

### 3. Добавление отдельной транзакцией в конец

В toolbar добавить независимые действия «Картинка» и «Файл». Команда сначала проверяет наличие редактора и актуальный maxBlocks, затем генерирует ID через createId, вставляет один узел в конец и выделяет его. Курсор/текстовое выделение не используются как диапазон замены. Нового завершающего paragraph автоматически нет: это соблюдает условие «один клик — один блок» и последний свободный слот.

Состояние disabled обновляется при изменении документа и лимитов; проверка внутри команды защищает от устаревшего состояния UI. Отказ не создаёт ID, транзакцию изменения или onChange. Логику выбора позиции, доступности и удаления вынести в небольшие тестируемые функции/адаптеры по текущему подходу unit-тестов.

### 4. Штатная история и адресное удаление

Использовать UndoRedo и транзакции существующего редактора. Явно отделять операции вставки/удаления от соседнего ввода и друг от друга границами истории; одного вызова dispatch недостаточно для гарантии отдельного шага undo. ID задаётся до вставки и сохраняется при восстановлении; экспорт никогда не генерирует ID.

Обработчик Backspace для NodeSelection image/file удаляет выбранный узел и возвращает управление обычным текстовым обработчикам во всех остальных случаях. Удаление единственного узла оставляет пустой paragraph с ID через createId в той же операции, чтобы undo восстановил исходную заметку без лишнего абзаца. Не создавать свою историю или кнопки undo/redo. Конкретный адаптер истории тестируется без запуска Tiptap runtime; реальное взаимодействие передаётся на ручную проверку.

### 5. Сохранить нетекстовые блоки в лимитах и диагностике

blockText возвращает пустую строку для image/file. Проверка maxBlocks считает все узлы верхнего уровня. normalizeNote и normalizeTransaction сохраняют props и отсутствие content у нетекстового узла; его нельзя разбивать как paragraph.

В planContent сейчас есть ранняя остановка при remaining === 0. Требуется узкая адаптация планирования: заготовка после полностью помещающегося текста сохраняется при свободном слоте, даже когда текстовый бюджет равен нулю. Если уже отсечено непомещающееся текстовое содержимое, действует прежняя семантика префикса — нельзя перескакивать через отброшенный текст к поздним блокам. Та же логика применяется при загрузке и уменьшении лимитов. Не менять остальные правила переполнения и paste.

diffBlocks сравнивает содержимое с учётом типа, не читая textColor/content у file. Неизменённые заготовки не создают ложных UPDATE. Расширенные снимки проходят существующие request preview, debounce и storage; новые endpoints и изменение таймингов не нужны.

### 6. Локальная проверка

Расширить имеющиеся model/limits/request/storage тесты смешанными fixtures и добавить тесты команд заготовок. Проверять контракт вставки, удаления, границ истории, ID и JSON round trip; не выдавать mock-тесты за проверку работы браузера или реального UndoRedo. Конкретные команды перечислены в tasks. Штатного локального type-check в package.json нет; полный tsc/build не использовать как замену.

## Risks / Trade-offs

- Отсутствующий content затрагивает типизированных потребителей → сузить union по type и адаптировать непосредственно затронутые обращения, без постороннего рефакторинга.
- Нормализация может незаметно вернуть content: [] или отбросить вложение после полного текстового бюджета → unit-тесты обоих путей нормализации и JSON round trip.
- Disabled-кнопка не принимает фокус и может мешать выбору узла → отдельная выделяемая оболочка, ручной сценарий выделения/Backspace.
- История может группировать соседние действия → явные границы, проверки адаптера и передача реального undo/redo пользователю для ручной проверки.
- Новая версия читает прежние заметки, старая версия не знает image/file → откат к старому приложению не гарантирует чтение заметки с заготовками.

## Migration Plan

Миграция существующих paragraph/heading и новый storage key не нужны. Добавить поддержку новых типов одновременно в модель, конвертеры и runtime, затем проверить локальные сценарии. При откате сначала сохранить копию заметки и удалить заготовки в поддерживающей их версии; автоматическое удаление пользовательских блоков при откате не реализуется.
