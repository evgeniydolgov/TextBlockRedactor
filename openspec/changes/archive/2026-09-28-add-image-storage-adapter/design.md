# Design

## Context

См. [proposal.md](proposal.md). Текущий image — атомарный Tiptap NodeView с атрибутом `id` и неактивной кнопкой; преобразования всегда восстанавливают пустые props, а валидация отклоняет заполненные вложения. `TextEditorProps` пока передаёт только документ, callback и лимиты, расширения создаются один раз на экземпляр редактора. Backend и файловый SDK отсутствуют.

## Goals / Non-Goals

**Goals:**

- отделить редактор от транспорта и API хранилища небольшим типизированным контрактом;
- сохранить файловую ссылку как часть обычного image-блока и истории Tiptap;
- сделать получение изображения чисто визуальным асинхронным состоянием NodeView;
- дать приложению работающую в одной сессии замену сервиса без новой зависимости.

**Non-Goals:**

- определять готовность, безопасность или конфиденциальность загруженного файла;
- синхронизировать побочный эффект загрузки с undo, удалением блока или очисткой файлов;
- сохранять Blob между сессиями либо кэшировать результат между несколькими блоками;
- расширять тот же цикл на file-блок.

## Decisions

### 1. Внедрять один адаптер через props редактора

Публичный контракт:

```ts
type UploadedImage = { id: string; name: string }
type ResolvedImage =
  | { type: 'url'; url: string }
  | { type: 'blob'; blob: Blob }

type ImageStorageAdapter = {
  upload(file: File): Promise<UploadedImage>
  resolve(fileId: string): Promise<ResolvedImage>
}
```

`TextEditorProps.imageStorage` необязателен. Различимый union фиксирует владение ресурсом: прямой URL принадлежит провайдеру, а object URL для Blob создаёт и освобождает редактор. Альтернатива с прямым импортом fileService связывает переиспользуемый редактор с отсутствующим SDK; единый `Promise<string>` заставил бы адаптер создавать object URL без ясного способа освободить его.

Поскольку Tiptap-расширения создаются один раз, рядом с контроллером лимитов вводится небольшой контроллер текущего адаптера с `configure` и подпиской. `useTextEditor` обновляет его при смене prop, а существующие image NodeView получают уведомление, отменяют актуальность старого запроса и повторяют `resolve`. Это избегает пересоздания редактора и сохраняет один Tiptap instance на документ.

### 2. Хранить ID в существующем `props.url`

Для совместимости с уже выбранной BlockNote-подобной моделью `url` остаётся строковым полем, но редактор трактует его как непрозрачный ID. `name` и `caption` также становятся изменяемыми строками image-блока; остальные image props остаются ограниченными текущими defaults. Новая заготовка сохраняет пустые строки.

Image-узел Tiptap получает атрибуты `url`, `name` и `caption`. `blocksToTiptap` переносит их в узел, `tiptapToBlocks` объединяет их с неизменяемыми defaults, а валидатор принимает любые строки для этих трёх полей. File сохраняет прежнюю модель только с пустыми props. Так onChange, localStorage и диагностический UPDATE используют существующий путь без отдельного React state или второго документа.

### 3. Разделить image и file NodeView

Общая фабрика пустых вложений больше не соответствует поведению image. File остаётся простым атомарным placeholder, а image NodeView отвечает за скрытый `input type="file"`, кнопку, временные сообщения, `<img>` и повтор получения. Выбор файла вызывает только `adapter.upload`; успешный результат одной транзакцией `setNodeMarkup` обновляет attrs текущего узла, сохраняя его `id` и caption. Ошибка не создаёт транзакцию.

Обновление attrs остаётся обычным шагом истории: undo/redo восстанавливает снимок узла и не повторяет внешний вызов. Сам загруженный объект может остаться неиспользуемым в хранилище; удаление файлов требует отдельного жизненного цикла и не входит в этот change.

### 4. Получать изображение как состояние представления

При непустом `url`, при смене URL и при смене адаптера NodeView запускает `resolve`. Счётчик поколения или эквивалентный token не позволяет завершению старого Promise обновить DOM после нового запроса либо destroy. Результат `url` сразу назначается `img.src`; для `blob` NodeView создаёт object URL и сохраняет ссылку на него для освобождения перед заменой и в `destroy`.

Loading и error хранятся только в NodeView. Resolve и повтор resolve не dispatch-ят транзакции, поэтому не вызывают onChange и не засоряют историю. При отсутствии адаптера заполненный блок показывает недоступность получения, не изменяя props.

### 5. Демонстрационный адаптер хранит Blob в Map

`createMemoryImageStorage` замыкает `Map<string, Blob>`, создаёт ID через общий `createId`, возвращает `file.name` и разрешает ID обратно в Blob. Единственный экземпляр создаётся на уровне страницы вне цикла её рендеринга и передаётся в `TextEditor`.

Map — минимальная реализация контракта и не требует пакетов, backend или сериализации бинарных данных. После перезагрузки сохранённый ID закономерно не находится; этот результат отображается обычным состоянием ошибки resolve. IndexedDB отклонён как лишняя персистентность для демонстрации, а data URL/localStorage — из-за дублирования и роста размера заметки.

### 6. Проверять асинхронную логику вне браузера через выделенные функции

Создание адаптера, переходы upload/resolve и владение object URL следует вынести из DOM-склейки в небольшие функции или контроллеры с внедряемыми callback `createObjectURL`/`revokeObjectURL`. Это позволяет Vitest проверить успех, ошибки, устаревшие Promise и cleanup без браузерного стенда. NodeView остаётся тонким слоем DOM; его доступность и фактический file picker передаются пользователю для ручной проверки.

## Risks / Trade-offs

- [После перезагрузки memory adapter не знает сохранённый ID] → показывать штатную ошибку resolve и явно считать адаптер только демонстрацией одной сессии.
- [Upload — необратимый внешний побочный эффект, а транзакция с ID отменяема] → не обещать удаление объекта при undo; очистку сирот вынести в будущую интеграцию сервиса.
- [Promise завершается после смены блока или адаптера] → маркировать поколения запросов и игнорировать устаревшие результаты; освобождать только object URL, созданные редактором.
- [Повторные resolve скачивают один Blob несколько раз] → принять для минимальной версии; общий cache не добавлять до отдельного требования.
- [Реальный сервис может не разрешать скачивание до окончания проверки] → адаптер сообщает ошибку, а блок предлагает повтор; опрос статуса и alert-состояния проектируются отдельно.

## Migration Plan

1. Расширить модель и Tiptap attrs с пустыми defaults, поэтому существующие сохранённые заготовки загружаются без миграции.
2. Подключить адаптер в памяти на странице и активировать только image NodeView.
3. В будущем заменить переданный экземпляр реализацией над реальным сервисом; документ и код редактора менять не потребуется.

Откат удаляет prop, контроллер, memory adapter и интерактивный image NodeView. Сохранённые непустые image props после отката будут отклоняться старым валидатором, поэтому такой откат допустим только до появления пользовательских данных либо вместе с очисткой этих полей.
