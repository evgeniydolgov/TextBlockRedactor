# Design

## Context

См. [proposal.md](proposal.md). `planContent` уже оставляет подряд идущие вложения после исчерпания текстового бюджета, пока хватает `maxBlocks`; менять его не требуется. `imageNodeView` получает асинхронный результат загрузки и вызывает `updateImageAttachment` по текущей позиции. Сейчас команда проверяет только тип узла, поэтому занявший ту же позицию другой image-блок может получить чужой результат. Для file-блока аналогичная команда уже проверяет ID и пустой `url`.

## Goals / Non-Goals

**Goals:**

- Описать фактический порядок нормализации в спецификации лимитов.
- Привязать завершение загрузки к ID исходного image-блока и принимать результат только пока его `url` пуст.
- Сохранить обычную транзакцию обновления атрибутов, чтобы действующие `onChange`, сохранение и undo/redo работали как прежде.

**Non-Goals:**

- Менять `planContent`, формат заметки, интерфейс блока или контракт `imageStorage`.
- Объединять реализацию image и file или добавлять очистку уже загруженного файла во внешнем хранилище.

## Decisions

### Уточнение лимитов только в delta spec

Изменить формулировку требования `Trim initial content before rendering` и добавить сценарии для подряд идущих вложений и следующего текстового блока. Существующий `planContent` не изменять: это согласование спецификации с реализованным поведением. Альтернатива — обрезать все блоки после исчерпания текста — противоречит действующей спецификации `text-editor` и меняет продукт.

### Проверка исходного ID в момент завершения upload

При начале загрузки сохранить ID image-блока, а после завершения использовать актуальную позицию из NodeView. Перед транзакцией `updateImageAttachment` проверяет тип узла, совпадение ID и пустой `url`; при нарушении любого условия не создаёт транзакцию. Это покрывает удаление, замену другим image-блоком в той же позиции и заполнение блока, не блокируя редактирование во время загрузки. Альтернатива — проверка только в NodeView — оставляет команду незащищённой для других вызовов.

### Обновление NodeView при смене блока

Если Tiptap предлагает существующему image NodeView узел с другим ID, не переиспользовать его для новой сущности. Тогда новый блок получает собственное представление и обработчики, а поздний callback старого блока остаётся связан с исходным ID. Даже если поздний callback выполнится, проверка команды предотвратит запись в новый блок. Альтернатива — обновлять захваченный ID при каждом `update` — может переназначить незавершённую загрузку другому блоку.

## Risks / Trade-offs

- [Узел с тем же ID переместился] → использовать текущий `getPos()`; проверка ID выполняется непосредственно перед транзакцией.
- [Ответ пришёл после замены или заполнения] → команда ничего не записывает, поэтому не создаёт лишний `onChange` и шаг истории.
- [Загруженный объект остался во внешнем сервисе после игнорирования ответа] → жизненный цикл файлового сервиса не входит в этот change; адаптеру не добавляется операция удаления.
