# Design

## Context

См. [proposal.md](proposal.md). `createUpdateHandler` сейчас сразу сериализует
документ и вызывает `onChange`; `useTextEditor` подставляет новый обработчик
при рендере. `DocumentPage` подключает только `logNoteBlocks`.
Приложение работает в React StrictMode; проверяем собственную логику в Vitest Node.
Требования: [specs/text-editor/spec.md](specs/text-editor/spec.md).

## Goals / Non-Goals

**Goals:** отделить управление ожиданием от React и хранение от редактора;
сохранить один экземпляр Tiptap, формат блоков и небольшие файлы около 100–150 строк.

**Non-Goals:** копия документа в React state, универсальная система хранилищ,
очередь сетевой синхронизации, автоматические UI-тесты и тесты Tiptap runtime.

## Decisions

### 1. Публичная настройка и граница передачи

Добавить `saveDelayMs?: number` в `TextEditorProps`, значение по умолчанию 1000.
В начале `DocumentPage` разместить понятную константу `NOTE_SAVE_DELAY_MS = 1000`
и передавать её через `<TextEditor saveDelayMs={NOTE_SAVE_DELAY_MS} ... />`.
Не добавлять пользователю приложения поле ввода настройки.

Отложить существующий `onChange`, а не вводить параллельный `onSave`: так наружу
не уходят промежуточные изменения, как запрошено. Сохранение остаётся обработчиком
страницы; TextEditor ничего не знает о localStorage. `0` отключает задержку;
не конечные, отрицательные и превышающие 2147483647 значения заменяются на 1000.

### 2. Независимый контроллер ожидания

Небольшой модуль `src/editor/model/createDebouncedChange.ts` управляет последним
снимком, одним таймером, актуальным callback и операциями schedule/flush/cancel/configure.
На изменение брать снимок через существующее преобразование блоков и заменять
предыдущий ожидающий снимок; не накапливать историю. Это позволяет завершить
передачу после уничтожения редактора, не обращаясь к его getJSON в cleanup.
Альтернатива — читать getJSON только при timeout — экономит сериализацию, но
усложняет сохранение при разрушении редактора и для текущего объёма не нужна.

Контроллер создаётся ленивой инициализацией useState хука и остаётся стабильным;
обычные рендеры не сбрасывают ожидание. Это не копия документа в React state:
там хранится только экземпляр контроллера, без обновления state при вводе.
Смена callback обновляет ссылку, смена delay перезапускает ожидание с текущего
момента, удаление callback отменяет ожидающий вызов. Без callback нет сериализации.
flush сначала снимает pending и отменяет таймер, затем вызывает callback один раз.
Повторные flush безопасны; cancel очищает снимок и таймер.
Начальная загрузка и перемещение выделения не вызывают schedule.

### 3. Уход со страницы

Небольшой адаптер lifecycle подписывается на `visibilitychange` (только hidden)
и `pagehide`; оба вызывают flush. Cleanup хука тоже выполняет flush и удаляет
подписки/таймеры. Запись в localStorage синхронная; Promise и сеть здесь не нужны.
Адаптер принимает цели событий как зависимости, чтобы тестировать его без браузера.
Повторный setup после cleanup, включая StrictMode, должен оставаться работоспособным.

Скрытие вкладки также считается уходом: это позволяет сохранить раньше завершения
процесса. Выбор событий основан на [MDN visibilitychange](https://developer.mozilla.org/en-US/docs/Web/API/Document/visibilitychange_event)
и [MDN pagehide](https://developer.mozilla.org/en-US/docs/Web/API/Window/pagehide_event).
Не использовать диалог подтверждения ухода или устаревший unload.

### 4. Хранилище одной заметки

Добавить `src/pages/document/storage/noteStorage.ts` с постоянным ключом
`text-block-redactor:note:v1`. Значение — JSON.stringify(NoteDocument), без
обёртки Tiptap, отдельного ID заметки или новых полей блоков.
Ключ вынесен в константу; он техническое имя, а не ID сущности.

Чтение выполнить до создания редактора через ленивую инициализацию страницы;
загрузить массив через JSON.parse и существующий validateNote. Не вводить проверку
UUID. Пустой массив отдаётся редактору как есть — он создаёт пустой блок.
Начальный снимок можно держать в state, но не обновлять его на каждый ввод.

Изолировать доступ к localStorage, включая получение свойства window.localStorage,
в try/catch. Адаптер принимает минимальный интерфейс getItem/setItem либо его getter
для Node-тестов. Возвращать явный результат чтения/записи вместо падения страницы.
Нет записи — обычный пустой документ. Ошибка — пустой документ и краткое сообщение
в существующем footer. При mount не удалять и не перезаписывать повреждённую запись;
последующее редактирование является основанием записать новый снимок.

Обработчик страницы сохраняет блоки и вызывает существующий logger один раз на
полученный снимок. Footer сообщает «Автосохранение на этом устройстве» либо ошибку;
не вводить ложный постоянный статус «Сохранено» во время ожидания.
Успешная запись снимает прежнее сообщение об ошибке.

### 5. Проверки

Vitest fake timers проверяют границу 999/1000 мс, перезапуск и последний снимок,
другую задержку, 0 и некорректные значения, смену callback/delay, cancel/flush,
повторный cleanup/setup. Заглушки событий проверяют подписки, hidden/pagehide,
отсутствие двойного вызова и продолжение работы после возвращения.
Заглушка storage проверяет round trip, пустое/отсутствующее значение, ошибку
доступа/getItem/setItem, повреждённый JSON, неподдерживаемые блоки и сохранение ID.
Композиционный unit-тест соединяет наш контроллер с нашим обработчиком сохранения:
во время ввода записей нет, после паузы или flush сохранён последний снимок.
Не создавать Editor, DOM, UI и скриншот-тесты. Новые модули включить в coverage.

## Risks / Trade-offs

- Принудительное завершение браузера без событий → гарантировать flush невозможно;
  hidden/pagehide покрывают обычный уход, запись также происходит после паузы.
- localStorage недоступен или заполнен → редактирование продолжается, ошибка видна.
- Несколько вкладок → действует последняя успешная запись; синхронизация вне задачи.
- Изменение частоты onChange → обновить публичный пример и тесты старого поведения.
- Неархивированные delta → перед будущей синхронизацией сначала применить
  blocknote-compatible-note-model, затем use-uuid-v7-block-ids, затем эту delta.

## Migration Plan

Данные прежней версии не мигрируются: сохранения ещё не было. Во время apply обновить
README, docs/note-blocks.md, conventions, acceptance и контекст openspec/config.yaml.
Основную спецификацию синхронизировать отдельным workflow; при этом обновить Purpose,
который пока говорит «без сохранения». Старые завершённые proposals не переписывать.
При откате кода запись localStorage не удалять; старая версия просто её не читает.
