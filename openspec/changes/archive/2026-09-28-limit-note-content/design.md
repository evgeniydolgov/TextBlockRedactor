# Design

## Context

См. [proposal.md](proposal.md). TextEditorProps сейчас содержит initialContent,
onChange и saveDelayMs. Расширения статичны в extensions.ts; собственные адаптеры
ID работают с транзакциями. prepareInitialDocument создаёт общий начальный блок
для редактора и preview. tiptapToBlocks объединяет content[].text одного блока.
Сохранение и диагностика уже подключены к одному отложенному onChange.

## Goals / Non-Goals

**Goals:** ограничения до отображения загруженного/вставленного контента,
одинаковые правила для редактора и его выходного документа, сохранение ID и курсора.
**Non-Goals:** сетевые ограничения, подсчёт размера JSON в байтах, UI счётчиков,
новые зависимости, тестирование внутренностей Tiptap или автоматический браузер.

## Decisions

### 1. Настройки и единица длины

Добавить три опциональных числовых пропса: maxBlockCharacters, maxNoteCharacters,
maxBlocks. Общие defaults 8000/50000/100 и функция нормализации настроек находятся
в src/editor/limits/limits.ts. В DocumentPage значения вынесены в верхнюю константу
и передаются также в подготовку начального документа. Изменение одного пропса
не сбрасывает другие, 0 и нецелые/небезопасные числа заменяются default.

Точное определение: сумма .length строк text, UTF-16, не число графем и не байты.
Это выбранная локальная метрика, а не предположение о backend. Экранирование JSON
длину не увеличивает. Перед подсчётом объединять plain text фрагменты блока.
Разрез не должен разделять корректную surrogate pair: отступить на одну позицию,
перенести пару в продолжение либо отбросить, если она уже не помещается. При
maxBlockCharacters=1 emoji из пары целиком не помещается; обработка заканчивает
допустимый префикс без бесконечного создания пустых блоков. Графемные кластеры
не сохраняются как неделимые единицы; это явно описать в документации.

### 2. Чистая нормализация загрузки

src/editor/limits/normalizeNote.ts обходит блоки по порядку и расходует бюджеты.
Длинный блок режется на части; первая сохраняет id/type/props, продолжения имеют
default paragraph props и createId. Пустые исходные блоки занимают по одному месту.
При достижении maxBlocks или исчерпании общего текстового бюджета отбросить хвост
заметки; точное попадание в границу не создаёт дополнительный пустой paragraph.
При пустом входе сохранить существующее правило одного пустого блока.

Нормализация не мутирует вход, идемпотентна для допустимой заметки и не генерирует
ID для отброшенных частей. Генератор передаётся зависимостью для unit-тестов.
Структурная validateNote остаётся отдельной: лимиты не означают разрешение
неподдерживаемых типов/полей. Новые ID не должны совпадать с входными.

prepareInitialDocument применяет нормализацию один раз перед инициализацией
preview и TextEditor. Самостоятельный TextEditor также нормализует initialContent
в createEditorOptions до создания Editor. Повторный проход на странице не меняет
ID. Mount не пишет storage: старая запись может оставаться большой до следующего
изменения, но не попадает в отображение и будущий save целиком.

### 3. Ввод и вставка: сохранять существующее содержимое

Не обрезать весь документ после каждой вставки: это могло бы удалять существующий
текст после курсора. Чистый планировщик fitInsertion учитывает документ, выделение,
вставляемый plain text/поддерживаемые блоки и лимиты. Сначала освобождается бюджет
выделения; затем принимается максимальный последовательный префикс вставки,
помещающийся с учётом разбиения и сохранения невыделенного хвоста.
Нельзя пропускать не поместившуюся середину и вставлять последующие части.
Проверка кандидата выполняется без генерации ID; назначать их только принятому
результату. Если ввод не меняет документ, не отправлять транзакцию обновления.
В реализации fitInsertion получает безопасные границы префиксов и чистые функции
построения/проверки кандидата. Адаптер учитывает выделение локальной заменой в новой
транзакции, не применяя её к состоянию редактора, и проверяет весь полученный текст.

Для обычного текста и paste подключить тонкие обработчики handleTextInput/handlePaste
в собственном расширении ContentLimits. Не заменять всю заметку через setContent
после onUpdate: это поздно и нарушает историю/курсоры. Применять локальную замену
диапазона и разбиение блоков в одной операции с отображением позиции курсора.
Переполнение H1–H3 всегда создаёт paragraph, следующий существующий блок не
используется как ёмкость для продолжения. Его ID и текст сохраняются.

### 4. Транзакционные ограничения и история

Добавить фильтр для остальных путей изменения (Enter, команды, IME, undo/redo),
который отклоняет операции, не помещающиеся по общему объёму или числу блоков
после необходимого разбиения. Допустимое переполнение отдельного блока исправлять
appendTransaction до обновления представления, с mapping выделения и защитой от
повторной нормализации. Не менять транзакцию внутри filterTransaction.
Официальные точки расширения описаны в [ProseMirror Reference](https://prosemirror.net/docs/ref/).

Адаптер применяет тот же чистый расчёт, а не независимую арифметику. Сначала
планируются изменения текста/границ, потом ID; учитывать UniqueID и BlockIdentity,
не вызывать строгий экспорт блоков до завершения назначения ID новым узлам.
Авторазбиение должно входить в исходную операцию undo. Отклонённая транзакция
не меняет pending autosave; onChange сериализует только окончательное состояние.
Особенно проверить выбор позиции курсора на границе и при вводе в середине блока.

Лимиты хранятся в стабильном состоянии отдельного экземпляра, не в глобальной
переменной extensions.ts. Изменение пропсов обновляет настройки и нормализует
текущий документ в layout-фазе до следующей отрисовки. При фактической обрезке
получается обычное изменение для autosave/preview; при увеличении — только новая
настройка. Старые операции истории, нарушающие актуальные лимиты, фильтруются.
Отброшенное при initial load содержимое вообще не входит в историю редактора.
Обрезка при смене пропсов имеет addToHistory=false: история сопоставляется через
локальные удаления/разбиения, сама обрезка не становится отменяемой операцией.

Проверено по установленным исходникам: UniqueID имеет priority=10000; ContentLimits
использует 50 и работает после назначения ID и heading input rules (100).
Editor.dispatchTransaction вызывает state.applyTransaction до view.updateState и
сериализует один итоговый update. ProseMirror history присоединяет appendTransaction
к исходной операции; дополнительная нормализация после ввода не получает addToHistory=false.

### 5. Проверки и структура

Файлы limits.ts, textBudget.ts, normalizeNote.ts, fitInsertion.ts и тонкие адаптеры
под src/editor/limits; при необходимости разделять в пределах 100–150 строк.
Unit-тесты только нашей логики: данные блоков и минимальные заглушки транзакций,
без Editor runtime, UI и скриншотов. Перед apply проверить точный порядок вызовов
на установленной версии по исходникам Tiptap/ProseMirror, особенно append/историю;
это конкретная проверка интеграции, не повторное проектирование требований.
Покрыть границы 7999/8000/8001, 49999/50000/50001, 99/100/101 и малые кастомные
значения, позволяющие компактно проверить комбинации. Проверить составной ввод,
merge/split, undo/redo адаптеры, частичный paste с выделением и неизменность хвоста,
Unicode, все три лимита одновременно и выход autosave/preview/диагностики.

## Risks / Trade-offs

- Обрезка теряет хвост → это согласованное поведение; при вводе защищается прежний
  невыделенный текст, при загрузке/уменьшении настроек сохраняется префикс заметки.
- Browser composition и история сложнее чистых функций → CLI проверяет наши решения,
  реальные сценарии IME/курсора передать пользователю, не выдавать unit за UI проверку.
- .length не равна числу видимых символов → явно описать метрику и пример emoji.
- Смена лимита во время ожидания save → заменить pending последним нормализованным
  снимком; не отправлять старое превышение при уходе со страницы.

## Migration Plan

Миграции формата storage нет. Чтение подготавливает допустимый начальный документ;
следующее сохранение заменяет запись по обычным правилам. Обновить README,
docs/note-blocks.md, docs/block-api-requests.md и контекст OpenSpec. При откате
ограничения снимаются, уже отброшенный и перезаписанный текст не восстанавливается.
