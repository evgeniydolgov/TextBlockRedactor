# Design

## Context

Мотивация — в proposal.md. Сейчас UniqueID использует свой UUID v4 по умолчанию, createEmptyNote и splitWithBlockIds — crypto.randomUUID. validateNote проверяет непустую строку и дубликаты; tiptapToBlocks также вызывает validateNote. В fixtures используются короткие строки a/p1/h1. uuid 14.0.2 уже установлен транзитивно, пакет ESM с TypeScript и лицензией MIT. Рабочее дерево перед proposal чистое.

## Goals / Non-Goals

**Goals:** единый UUID v7 для генерации всех новых ID данных заметки и сохранение идентичности первого фрагмента. Переданные ID сохраняются независимо от версии UUID. Правило генерации распространяется на будущие ID сущностей через соглашения проекта.

**Non-Goals:** удаление механизмов UniqueID, переписывание его плагина, миграция внешних данных, сортировка блоков, добавление пока не существующего ID заметки и изменение статических имен типов/DOM-якорей.

## Decisions

### Общий модуль ID

Добавить `src/shared/ids.ts` с `createId(): string`, вызывающим `v7()` из uuid без options. Production-проверку isUuidV7 не добавлять; validate/version можно использовать в unit-тестах для проверки результата нашего генератора.

Официальный [uuid API](https://github.com/uuidjs/uuid#uuidv7options-buffer-offset) поддерживает v7. Закрепить uuid 14.0.2 как прямую runtime-зависимость и обновить lockfile; не полагаться на транзитивный импорт. Самостоятельный UUID-алгоритм и изменение цифры версии в UUID v4 недопустимы.

### Три точки подключения

- UniqueID.configure получает `generateID: () => createId()`; обертка явно не передает контекст node/pos как options в uuid.v7. [Документация generateID](https://tiptap.dev/docs/editor/extensions/functionality/uniqueid#generateid).
- createEmptyNote использует createId по умолчанию, сохраняет инъекцию генератора для unit-тестов.
- splitWithBlockIds использует тот же default-генератор; алгоритм назначения старого ID первому фрагменту не меняется.

UniqueID и uuid решают разные задачи: первый управляет жизненным циклом ID узлов, второй создает строку нужного формата. Сохранение расширения позволяет ограничить изменение форматом идентификаторов.

### Совместимость существующих ID

validateNote не меняется: проверяет непустую строку и точные дубликаты строк. Проверка версии UUID, нормализация регистра и автоматическая замена существующих ID не добавляются.

blocksToTiptap и tiptapToBlocks продолжают использовать текущий валидатор. Документ может содержать старые ID вместе с новыми UUID v7. Короткие строки в существующих fixtures остаются допустимыми; массовая замена примеров и fixtures не нужна.

### Проверки нашей логики

- Unit-тесты createId проверяют формат/версию результата и несколько различных вызовов; без попытки доказать уникальность математически или тестировать алгоритм uuid.
- Инъекция генератора в тестах фабрики и split сохраняется; default-путь отдельно проверяет v7 и сохранение первого ID любого допустимого строкового формата.
- Проверка нашего конфигурирования UniqueID через заглушку configure или выделенные опции: callback использует createId и игнорирует контекст редактора. Не создавать Editor и не запускать внутренний алгоритм Tiptap.
- Добавить регрессионную проверку загрузки/round trip смешанных ID (UUID v4, UUID v7, короткая строка) без замены. Существующие проверки пустых строк и точных дубликатов сохраняются.
- Добавить общий модуль в coverage.include; выполнить CLI test/coverage/build/lint/spec:validate. Браузер, UI и screenshots исключены.

## Risks / Trade-offs

- Пропущенная точка UUID v4 → поиск randomUUID/v4/generateID/generateId по production-коду и тесты трех точек подключения.
- Смешанные форматы в документе → документировать, что UUID v7 гарантируется для новых ID, а не для ранее переданных; миграции и проверки версии нет.
- uuid содержит время генерации → не использовать его как средство определения порядка блоков или авторизации; дополнительных возможностей не добавлять.
- Предыдущая блочная модель еще не архивирована → новый delta добавляет отдельное требование, не копирует и не переопределяет старые сценарии; завершенные changes не редактировать.

## Migration Plan

Прямая зависимость и общий модуль → три генератора → unit-тесты → документация и CLI-проверки. Проверка входных данных остается прежней; миграция ID не нужна. Коммит и решение об архивации остаются пользователю.
