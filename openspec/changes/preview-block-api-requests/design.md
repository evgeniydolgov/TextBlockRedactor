# Design

## Context

Мотивация и границы — [proposal.md](proposal.md). `useTextEditor` уже передаёт
NoteDocument после задержки, а `createNoteSaveHandler` сохраняет, сообщает ошибку
и вызывает logger. `DocumentPage` читает localStorage до монтирования редактора.
При пустом входе `createEditorOptions` сейчас сам создаёт начальный блок; этот
ID пока неизвестен странице. Есть Vitest Node и тест композиции autosave.

## Goals / Non-Goals

**Goals:** чистый детерминированный diff, типизированные описания API, отдельная
сессия сравнения и минимальная интеграция в существующий save handler.

**Non-Goals:** изменение блочной модели, HTTP-слой, серверная очередь, подтверждения,
переиспользование DTO как модели редактора и реализация перестановок.

## Decisions

### 1. Модули и типы

Добавить `src/blocks/requests/` с небольшими файлами около 100–150 строк:
`types.ts`, `diffBlocks.ts`, `buildBlockRequests.ts`, `createRequestPreview.ts`.
Logger разместить рядом с `logNoteBlocks` на странице. При необходимости выделить
сравнение блока и выделение новых групп в отдельные функции/файлы.

Типы описаний — discriminated union по method/path/body для четырёх эндпоинтов.
Типы тел структурно воспроизводят пользовательский контракт для NoteBlock:
CreateBlockRequest { block, position? }; BlocksListRequest с operation CREATE/DELETE,
blocks?, ids?, position?, noteId?. Конструкторы заполняют только применимые поля.
PUT передаёт полный NoteBlock, DELETE не имеет body. Сегмент blockId кодируется
через encodeURIComponent; ID внутри тела остаётся исходным, без проверки UUID.
Не устанавливать @blocknote/core ради типов: наша модель уже описывает поддерживаемое
подмножество Block. NoteBlockDTO с noteId/числовым position — ответ API, здесь не нужен.

### 2. Сравнение и сборка запросов

Сопоставить прошлые/текущие блоки по ID через Map. Отсутствующие текущие ID — DELETE;
новые — CREATE; общие ID с изменёнными поддерживаемыми полями — UPDATE.
Сравнивать type, props по полям, plain text как объединённую строку и children
поддерживаемой модели. Не использовать JSON.stringify целого блока как равенство:
порядок ключей и границы текстовых фрагментов не являются изменением содержимого.
В PUT/CREATE сохранять полный текущий блок, не превращать его в патч.

Порядок выдачи: DELETE, затем PUT в текущем порядке, затем CREATE слева направо.
Одно удаление — DELETE /blocks/:id; два и более — POST /blocks/list с ids
в прежнем порядке. Удаляемые блоки могут быть несмежными: запрос адресует ID.
Для CREATE выделить максимальные непрерывные группы новых ID в текущем массиве.
Один элемент — POST /blocks; несколько — POST /blocks/list с blocks в этом порядке.
Внешние соседи каждой группы являются сохранившимися ID, поэтому не требуют
ссылок на ещё не созданные блоки и уже существуют после стадии DELETE.

Подтверждённая семантика: для [A, X, Y, B] position = { before: A.id, after: B.id }.
При отсутствии левого/правого соседа соответствующее поле равно null; передавать
оба поля явно. Пример замены [A,B,C,D] → [A,X,Y,D]: удалить B/C, создать X/Y
между A/D. Сдвиг индексов у A/D не создаёт PUT. Группового UPDATE в API нет.
Полная перестановка общих ID вне области поддержки: сравнение не создаёт для неё
MOVE или искусственную пару DELETE/CREATE. Документировать это ограничение.

### 3. noteId

Построитель и preview принимают `noteId?: string`. Страница получает его опционально
через props и передаёт в адаптер; текущий App может не передавать ничего.
При наличии включать noteId только в групповые операции. При отсутствии поле
опускается согласно предоставленному типу; не использовать заглушку, UUID или null.
В одиночном CreateBlockRequest поле noteId не объявлено — не добавлять его ни
в body, ни в block. Это точное воспроизведение контрактов, а не обещание пригодности
к отправке без контекста заметки. Для другой заметки требуется новая смонтированная
страница/сессия, как и для существующего initialContent; переключение заметок вне задачи.

### 4. База и начальный пустой блок

Вынести подготовку начального снимка страницы в небольшую функцию: непустой
загруженный массив использовать как есть, иначе один раз вызвать createEmptyNote.
Тот же массив передать в TextEditor.initialContent и в preview. Создание блока
происходит до редактора, так что ID не расходятся. Для самостоятельного TextEditor
его существующий fallback остаётся. Не вызывать onChange ради инициализации.

Сессия хранит detached copy начального документа. При onChange строит запросы
между базой и снимком, после успешного построения обновляет базу его копией, даже
если запросов нет или запись localStorage не удалась. Это последняя обработанная
версия preview, а не последнее успешное сохранение и не серверное подтверждение.
Первый ввод в начальный пустой блок — PUT; ввод и полное undo до паузы — пустой diff.
Если после выведенного DELETE блок восстановлен undo, его прежний ID даёт CREATE.
Новая сессия после reload начинается с фактически загруженного локального состояния.

### 5. Интеграция и консоль

Добавить в createNoteSaveHandler зависимость preview, сохранив запись localStorage,
reportError и logNoteBlocks. Один callback вызывает существующее сохранение и preview;
таймер не дублируется. Ошибки storage уже представлены результатом, не исключением,
поэтому не препятствуют preview. Результат — detached массив объектов; logger
вызывает console.log('[note:requests]', requests), только если массив непустой.
Снимки базы, входа и ранее выданных тел не должны разделять изменяемые вложенные
объекты; использовать structuredClone на границах сессии/выхода. Чистые функции
не обращаются к React, Tiptap runtime, storage или console.

### 6. Последний цикл в localStorage

Добавить маленький адаптер `src/pages/document/storage/requestLogStorage.ts`.
После получения результата записи заметки и построения запросов записать JSON-объект
под ключом `text-block-redactor:request-log:v1`:

```ts
{ requests, storage: { key: 'text-block-redactor:note:v1', data, success, error } }
```

requests — те же описания, что предназначены для консоли; data — полный снимок,
переданный в save заметки, а не только изменённые блоки. success отражает результат
основной записи; error — её сообщение об ошибке либо null при успехе.
Это диагностика сформированных запросов и попытки setItem, не исполнение HTTP.

Один onChange/flush — один цикл. Каждый цикл перезаписывает объект, в том числе
при requests: []; иначе после отмены изменений там остались бы старые операции.
Mount, выделение и повторный flush без pending не меняют запись. Историю не читать,
не накапливать, не добавлять время/ID. После reload запись доступна для просмотра,
но не используется для восстановления заметки или базы preview.

Запись диагностики выполняется после попытки основной записи. Её ошибка ловится
и выводится через console.warn, не меняет результат сохранения заметки и базу preview,
не ломает редактирование и не запускает повторный цикл. При недоступном storage
последний цикл может не записаться; старая запись не выдаётся за новый успешный цикл.

### 7. Проверки

Unit-тесты по сценариям спецификации: все тела и отсутствие лишних полей, соседние
и разделённые группы, границы, замена диапазона, split/merge, Unicode, пустой текст,
сохранение legacy ID и UUID v7, изменение type/level, семантическое равенство.
Проверить undo до и после передачи, неизменность входов/старого вывода, пустой diff,
инициализацию пустой заметки, опциональный noteId и кодирование пути.
Композиционный тест с fake timers и storage-заглушкой проверяет один цикл autosave,
ошибку записи, flush, отсутствие дублей и отсутствие операций mount. Проверить
перезапись единственного объекта последнего цикла, requests: [], точность data и
success/error, независимость ошибок основной и диагностической записи, отсутствие
чтения журнала для инициализации и отсутствие истории/временных меток.
Новые модули включить в coverage. Не создавать Tiptap Editor, UI и браузерные тесты.

## Risks / Trade-offs

- База preview не равна состоянию backend → явно документировать локальную симуляцию;
  подтверждения и очередь появятся только отдельной задачей подключения API.
- Начальный пустой блок считается существующим → согласованные ID и отсутствие
  ложного CREATE после отмены; реальный backend при подключении потребует своей базы.
- Группы используют подтверждённый порядок массива → сохранять это правило тестами.
- Перестановки не поддерживаются → не объявлять адаптер полным механизмом синхронизации.
- Копирование снимков → приемлемо для текущего минимального редактора, без новых зависимостей.

## Migration Plan

Основная запись localStorage не меняется, миграции нет; появляется отдельный ключ
последнего цикла. Обновить README, docs/note-blocks.md
и контекст OpenSpec; добавить docs/block-api-requests.md с контрактами и примерами.
При откате отключается preview, локальное сохранение продолжает работать.
